## 这是什么

TabNest 把互不相干的 Windows 应用窗口组织成一个标签工作区。把一个窗口拖到另一个窗口上，两者合并，上方出现一条标签栏；点标签切换，把标签拖出来就拆分回独立窗口。

```
┌──────────────────────────────────────────────────────────────┐
│  ▣ VS Code   │  ▣ 终端       │  ▣ Chrome   │  ▣ 资源管理器 ✕ │  ← 分组栏
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                     当前活动窗口                              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

它管理的是**窗口**，不碰应用内部。从不读取、修改或外传任何文档内容，也从不把代码装进别的进程。

> **状态 —— 0.1.1，该做的都已做完。** 分组、切换、拖拽合并与拆分、规则、已保存分组、热键、任务栏策略与设置中心均已可用。把标签画进窗口**原生标题栏**意味着向其他进程注入代码，而 TabNest 刻意不做这件事——见[路线图](#路线图)。**本版本未做代码签名**，见[未签名版本](#未签名版本)。

## 为什么做它

Windows 至今没有回答"一天开十二个窗口"这件事。Alt+Tab 是一张平铺列表，任务栏按应用而不是按任务归组，而微软的 Sets 已在 2019 年取消。剩下的方案都是商业软件，并且**无一例外**靠向系统里几乎每个进程注入 DLL 来工作。

TabNest 押的是相反的一边：待在所有其他进程之外，代价用工程量来付，而不是用用户的信任来付。

## 亮点

**零 DLL 注入。** TabNest 不向任何进程装载代码。观察走 `SetWinEventHook`（OUTOFCONTEXT），操作走普通窗口 API。你的浏览器、IDE、密码管理器里没有任何一行 TabNest 的代码。

**11.3 MB 单文件，无需运行时。** 裁剪 + 单文件 + 压缩 + 自包含。下载下来双击即用：不装 .NET 运行时，不装 VC++ 运行库，不要管理员权限。

**空闲开销压在测量分辨率的地板上。** 20 秒空闲采样的 CPU 占用低到测不出差别，常驻工作集 32 MB，15 个线程。产品里没有任何轮询，每一次唤醒都能追溯到一个真实的窗口事件。用 `TabNest.exe --benchmark` 可自行复现。

**窗口任何时候都能还原。** 每次窗口写操作**之前**先落盘快照。崩溃、强杀、卸载，窗口都会回到接管前的位置，任务栏按钮也会恢复。

**每个开关都真的有效。** 设置中心里的每一项都有对应的测试断言"改了之后行为确实不同"。**一个点了没反应的开关，比没有这个开关更糟。**

**以普通用户身份运行。** `asInvoker` 清单，无服务、无提权助手、无自动更新守护进程。

## 竞品对比

这个品类里唯一成熟的产品是 **Stardock Groupy 2**。TabNest 是刻意对标它做的，下面的数字全部来自实测而非估算。

> **测量方法。** Groupy 2 v2.3.1 与 TabNest 0.1.1，同一台机器（Windows 11 26100，x64，24 逻辑核），均在无鼠标键盘输入的状态下空闲 20 秒。内存与句柄取自进程表；CPU 由 `TotalProcessorTime` 差分得出；注入数通过遍历全部可读进程的模块表统计。Groupy 一列是其常驻进程之和（`GroupyCtrl` + `GroupySrv` + 两个助手）。TabNest 一列取四次测量的中位数，可用 `TabNest.exe --benchmark` 自行复现。完整原始数据与方法见 [`docs/competitive-analysis.md`](docs/competitive-analysis.md)。**你的数字会与此不同** —— 这是一台机器、一种配置、一个时间点的结果。

| | **TabNest 0.1.1** | Groupy 2（v2.3.1） |
|---|---|---|
| 许可 | **MIT，开源** | 商业，闭源 |
| 价格 | **免费** | 付费 |
| **向其他进程注入 DLL** | **无** | 测试机上 46 个进程 |
| 常驻工作集 | **32.1 MB** | 78 MB |
| 空闲 CPU（20 秒采样） | 0.00~0.08% | 单核 0.08% |
| 线程数 | **15** | 30 |
| 句柄数 | **343** | 706 |
| 下载体积 | **11.3 MB 单个 exe** | 24.6 MB 安装包 |
| 需额外安装运行时 | **否** | 否 |
| 后台服务 | **无** | 有（`GroupySrv`） |
| 深色主题 | **有** | 无 |
| 设置项搜索 | 暂无 | 无 |
| 标签画进原生标题栏 | 无 —— 刻意如此 | **有** |
| 替换资源管理器／记事本原生标签 | 无 | **有** |
| 按文档、按文件夹的规则 | 无 | **有** |
| 标签悬停预览 | 无 | **有** |
| 代码签名 | 暂无 | **有** |
| 成熟度 | 0.1.1 | 2017 年起持续发布 |

**空闲 CPU 那一行是打平，不是赢。** 单核 0.08% 在 20 秒里是 16 毫秒，正好一个调度时钟节拍，也就是这种测量方式的分辨率地板。Groupy 落在同样的 16 毫秒上。两者空闲时都是真的空闲，用这个方法谁也证明不了比谁强。这里如实写出来而不是悄悄删掉，是因为本表早先的版本声称了一个数据并不支持的差距。

**Groupy 确实更强的地方：** 集成标签、原生标签替换、文档级规则、悬停预览、已签名的二进制，以及多年积累的兼容性工作。前四项都必须在目标进程内部执行代码 —— 而这正是 TabNest 明确拒绝做的事，不是"还没做"，是不打算做。如果你需要标签画在真正的标题栏里，那就买 Groupy：它是个好产品，这个能力是它用 TabNest 不愿付的代价换来的。

### 不注入意味着什么

向系统里每个进程装载 DLL 是解决这个问题的标准做法，它的代价不会出现在任务管理器的任何一行里：

- **爆炸半径。** 注入 DLL 里的一个缺陷可以让宿主应用崩溃。一个 bug 会波及它被映射进去的每一个进程。
- **隐性开销。** 46 个进程各自承担 DLL 镜像与钩子分发的成本，这些都不会被算进工具自己的内存与 CPU。
- **信任面。** 运行在你浏览器和密码管理器内部的代码，能看到它们渲染的一切。TabNest 看不到，因为它根本不在那里。
- **杀软与沙箱。** 全局注入是终端安全最敏感的行为之一，而现代沙箱进程本来也会拒绝它。

这个取舍是诚实的，而且并不免费：待在外面意味着 TabNest 无法在窗口真正的标题栏上绘制，焦点转移也受 Windows 前台锁定的约束（见[已知限制](#已知限制)）。

## 安装

从 [Releases](../../releases) 下载其一即可：

- `TabNest.exe` —— 放到任意目录双击运行。不需要运行时，也不需要管理员权限。
- `TabNest-0.1.1-setup.exe` —— 可选安装包：开始菜单快捷方式、开机自启，以及卸载时先让运行中的实例把窗口还原回去。

配置与已保存分组存放在 `%LOCALAPPDATA%\TabNest\`，卸载时保留。

### 未签名版本

**0.1.1 没有做 Authenticode 代码签名。** 项目方尚未购买 OV/EV 证书。这是本版本的既定状态，不是安装包少了文件。

运行时可能遇到的情况，以及怎么处理：

1. **SmartScreen：「Windows 已保护你的电脑」。** 未签名的新文件都会这样。点**更多信息**，确认文件名是 `TabNest.exe` 或 `TabNest-0.1.1-setup.exe`，再点**仍要运行**。提示按文件哈希计算：安装包拦一次之后，装好的 `TabNest.exe` 第一次启动还可能再拦一次。
2. **杀毒软件隔离，或报木马。** 未签名的窗口管理工具是常见误报类型。如果你信任 GitHub 上的源码，从隔离区恢复即可。环境不允许运行未签名程序就不要用这一版。
3. **公司电脑直接禁止未签名程序。** 没有「仍要运行」可点。这时需要签过名的构建，或找 IT 开白名单。

**官方不提供已签名的二进制。** 若你需要签名版（少弹 SmartScreen、进企业白名单），请**自行购买 OV 代码签名证书**（DigiCert、Sectigo 等），再用 `signtool` 带时间戳分别签 `TabNest.exe` 和安装包。仅为了过 SmartScreen **不必买 EV**。开源维护者也可以向 [SignPath Foundation](https://signpath.org/) 申请由其代签。证书如何接到本仓库的打包脚本，见 [`packaging/README.md`](packaging/README.md)。

### 运行环境

Windows 10 2004（内部版本 19041）及以上，x64 或 ARM64。需要启用桌面窗口管理器（DWM），并开启*"拖动时显示窗口内容"* —— 两项 TabNest 都会自检并在未满足时明确提示。

## 从源码构建

需要 [.NET 10 SDK](https://dotnet.microsoft.com/download)（版本由 `global.json` 锁定）。不需要 Visual Studio。

```bash
dotnet build
```

```bash
dotnet test
```

生成可发布的单文件产物：

```bash
dotnet publish src/TabNest.App -c Release -r win-x64 -o publish/v1 --self-contained true -p:PublishTrimmed=true -p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true
```

### 诊断与测试模式

TabNest 内置一批无需图形界面的诊断模式：

```bash
dotnet run --project src/TabNest.App -- --diagnose
```

| 模式 | 作用 |
|---|---|
| `--diagnose` | 列出全部窗口，并用人话解释每个窗口为何能或不能被分组 |
| `--benchmark` | 按上表的目标测量内存、线程、句柄、空闲 CPU 与延迟，任一项退步即返回非零退出码 |
| `--watch` | 实时跟踪拖放命中判定链路 |
| `--selftest` | 分组 → 切换 → 拆分 → 还原闭环，并测量切换延迟 |
| `--grouptest` | 同上，但走**生产代码路径** |
| `--railtest` | 验证分组栏可见、位置正确且未被遮挡 |
| `--settingstest` | 校验设置中心的布局、命中与写回接线 |
| `--quirktest` | 针对"有脾气的窗口"的回归套件（见下） |
| `--stresstest` | 事件风暴与句柄泄漏检测 |

集成测试模式需要先启动测试宿主：

```bash
dotnet run --project tools/TabNest.Harness -- --spawn normal,stubborn,fixed,hideonclose
```

测试宿主**刻意**生成一批行为恶劣的窗口，因为听话的窗口什么也证明不了。`stubborn` 模仿 Chromium —— 在 `WM_WINDOWPOSCHANGING` 里把自己的最大化矩形强行改回去，Electron 应用就是这么干的；`hideonclose` 关闭时只隐藏不退出；`fixed` 把自己的尺寸锁死。每一个的存在，都是因为它抓到过一个普通 WPF 窗口轻松放行的真实缺陷。

## 架构

```
src/TabNest.Core      纯领域层：组状态机、规则引擎、快照、配置。
                      零 Win32，可 100% 单元测试。
src/TabNest.Interop   全部 P/Invoke、窗口观察、窗口控制、任务栏控制。
src/TabNest.App       常驻托盘进程、编排、分组栏、设置中心。
                      全部 Win32 + GDI/GDI+ 自绘 —— 不含任何 WPF。
tests/                领域层单元测试（196 个）。
tools/TabNest.Harness 疑难窗口测试宿主，不随产品发布。
```

三条规则撑起整个设计：

**领域层从不碰窗口。** `GroupSessionManager` 是纯状态机，只产出 `WindowAction` 指令，由 `WindowController` 在单一串行队列上执行。因此组逻辑可以在屏幕上没有任何窗口的情况下被完整测试。

**任何地方都不用 WPF。** WPF 无法裁剪（启用 `PublishTrimmed` 时 SDK 直接报 `NETSDK1168`），也不支持 NativeAOT。保留它意味着自包含发布 135 MB，或强制用户安装运行时；摘掉之后是 11.3 MB 零依赖可执行文件。`--benchmark` 会断言 `PresentationFramework` 从未被加载。

**任何跨进程同步消息必须带超时。** 统一走 `SendMessageTimeoutW`，操作前用 `IsHungAppWindow` 预检。目标程序假死绝不能拖垮 TabNest。

更长的工程笔记 —— 包括催生这些规则的那些失败 —— 见 [`docs/development.md`](docs/development.md)。

## 已知限制

**没有前台权限时，焦点转移会降级。** 注入到目标进程里的代码天然继承该进程的前台权限；TabNest 在进程外，受 Windows 前台锁定机制约束。用户点击标签时，TabNest 收到了最后一次输入事件，按规则即获得前台权限，此时焦点能正常转移。但在没有用户输入的场景（例如脚本调用）下，四级降级链会退到"仅置顶"：窗口来到最前，键盘光标却仍在原处。这是降级而非失败，`--selftest` 会如实区分这两种结果。

**分组栏是独立窗口，因此可能慢一帧。** Groupy 的标签栏毫无缝隙，是因为它由注入的代码画在窗口自己的标题栏上。TabNest 的分组栏从外部追随目标窗口，原理上在快速拖动时必然落后一帧。目前靠向下覆盖窗口顶部圆角来消除视觉接缝。要彻底消掉这最后一帧延迟，只能从目标进程内部绘制，而 TabNest 不做这件事。

**规则界面是应用清单，不是规则编辑器。** 分组规则页是一份可执行文件列表加一个*"仅允许指定应用在组中"*复选框：不勾时是阻止清单，勾上时是允许清单。完整的规则引擎（进程 + 窗口类 + 标题的组合匹配、部分匹配、子规则、优先级）照常可用，但只能在 `settings.json` 里手工配置。为了覆盖少数复杂场景而让所有人面对一张多字段表单，是把成本摊错了地方；手工规则不会被界面覆盖，页面上会提示它们的存在。

**整组全屏用的是"假最大化"。** Chromium 系应用在最大化状态下会把自己的矩形强行改回整个工作区，真正最大化的窗口因此让不出分组栏需要的那一条。TabNest 改为把窗口还原成普通窗口，再铺满"工作区减去分组栏"。视觉上完全一致，但系统不认为该窗口处于最大化，这会影响最大化按钮的图标与贴靠布局。

**尚未实现：** 集成标签与原生标签替换（均需注入，属刻意不做，见[路线图](#路线图)）、热键重绑界面（热键可查看、可整体开关，改绑需编辑 `settings.json`）、代码签名。

## 路线图

**TabNest 不注入，也没有开始注入的计划。** 标签就活在窗口上方那条分组栏里，这就是产品本身，不是通往别处的过渡形态。设置中心里没有模式开关，因为只有一种模式。

早先的计划里有个第二阶段，打算引入原生注入层把标签画进真正的标题栏。那个计划**已经搁置**。它能买到四样东西——集成标签、替换资源管理器与记事本的原生标签、代理 <kbd>Ctrl</kbd>+<kbd>T</kbd>/<kbd>N</kbd>、文档级规则——而每一样都要求在别人的进程里跑代码。对于大多数人选择这个工具的那条理由来说，这是一笔太大且不可逆的代价。

如果有足够多的人想要集成标签，不违背这个承诺的做法是**独立的可选下载**：默认发布的程序保持零注入，也保持干净的杀软画像。想要就来提 issue —— 能推动这件事的是真实需求，不是设想。

近期真正计划中的：代码签名、补截图，以及真实使用暴露出来的兼容性问题。

## 参与贡献

欢迎提 Issue 与 PR。本项目有两条特有的要求：

1. **回归测试必须先被亲眼看到失败，修复才能合入。** 不是"理应会失败"，而是真的拿它跑一遍未修复的代码、确认它变红。这个项目已经抓到过三个什么都没断言的测试，和一次悄悄没生效的撤销。
2. **疑难窗口先在测试宿主里复现。** 如果某个应用能让 TabNest 出问题，请先在 `tools/TabNest.Harness` 里加一种能复现该行为的窗口，再去修。一个全是听话窗口的测试宿主，什么也证明不了。
