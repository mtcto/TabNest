# 开发笔记

> 面向贡献者。产品介绍见 [README](../README.zh-CN.md)。
>
> 这里记的不是风格偏好，是硬性约束 —— 每一条背后都有一次真实的失败。违反它们会直接损害产品。

## 一、硬性约束

### 整个产品不使用 WPF

托盘、窗口观察、分组栏与设置中心全部走 Win32 + GDI/GDI+ 自绘。

WPF 不支持裁剪（启用 `PublishTrimmed` 时 SDK 直接报 `NETSDK1168` 拒绝构建），也不支持 NativeAOT。保留它意味着自包含发布 135 MB，或强制用户安装运行时；摘掉之后是 11.3 MB 零依赖单文件。

`PresentationFramework` 是否被加载由 `--benchmark` 自动校验 —— 这不是靠自觉维持的约定，是有门禁的。

### 设置项必须真的生效

每一个出现在设置中心的开关都要有对应的行为改变，并由 `SettingsEffectTests` 断言"改了设置，输出确实不同"。

曾经有 **12 个开关**能切换、能落盘、能命中，点了却毫无效果 —— 而当时三层测试全绿，因为它们验证的都是"能切换／能保存／能命中"，没有一个验证"切换之后行为真的变了"。根因是 `RefreshRail` 里写着 `new RailMetrics()`，把用户设置整份丢掉了。

**一个点了没反应的开关，比没有这个开关更糟。**

### 所有 P/Invoke 集中在 `TabNest.Interop.Native`

其他项目不得声明 `[LibraryImport]`。

### 领域逻辑不碰窗口

`GroupSessionManager` 是纯状态机，只产出 `WindowAction` 指令，由 `WindowController` 在单一串行队列上执行。这让组逻辑可以在无窗口环境下被完整测试。

### 任何跨进程同步消息必须带超时

统一走 `SendMessageTimeoutW`，操作前用 `IsHungAppWindow` 预检。目标程序假死不得拖垮 TabNest。

### 窗口状态必须可还原

每次窗口写操作**之前**先落盘快照。TabNest 崩溃、被强杀、被卸载，都不得留下位置错乱或隐藏的窗口。

卸载一个窗口管理工具却把用户的窗口弄乱，是最不可接受的收尾。

## 二、测试纪律

这三条是这个项目付出代价最大的部分。

### 回归测试必须先被亲眼看到失败

不是"理应会失败"，而是真的拿它跑一遍未修复的代码、确认它变红，再把修复加回去。

这条纪律至今抓到过：

- **两个什么都没断言的测试。** 其一，验证"关闭即隐藏的成员会被移出分组"的测试自己调用了 `SweepForTest` —— 也就是被测机制本身；其二，只用一个隐藏式窗口，导致分组在剩一个成员时自动解散，断言被平凡满足。
- **一次悄悄没生效的撤销。** 用字符串替换去撤销修复，因 CRLF 未能匹配，测试当然还是绿的。是坐标数字看着不对劲才发现。此后撤销一律按行号操作，并用 grep 核对撤销确实落地。

### 模拟用户输入的测试必须照抄系统真实的事件序列

少发一个事件就等于没测。

"全屏后分组栏仍可见"曾经测试全绿而功能全坏：测试直接调 `OnLocationChanged`，而系统真实的双击标题栏是 `MOVESIZESTART → 位置变化 → MOVESIZEEND`，首尾两个拖拽事件走的是完全不同的分支。

### 回归测试必须在发布产物上跑一遍

`dotnet build` 出来的 Debug 构建和裁剪单文件发布**不是同一个运行时环境**。

裁剪会把一批特性开关关掉，直接写进发布产物的 `runtimeconfig.json`。其中之一是：

```
"System.Runtime.InteropServices.BuiltInComInterop.IsSupported": false
```

于是所有 `[ComImport]` 接口在发布版里都不工作，`Marshal.GetObjectForIUnknown`
一律抛 `NotSupportedException`。

这不是理论风险。任务栏按钮策略用 `[ComImport]` 声明 `ITaskbarList`，
Debug 下工作正常、全部测试通过，而**每一个发布版里它都静默失效** ——
异常被 catch 吞掉，降级成"保留所有按钮"，日志里一个字都没有。
后来 AppUserModelID 判定踩了同一个坑，才在"拿发布产物再跑一遍 `--quirktest`"时暴露。

因此：

- COM 接口一律手写 vtable 函数指针（见 `Native/ComObject.cs`），不用 `[ComImport]`；
- 发版前必须执行 `publish\v1\TabNest.exe --quirktest`，不能只跑 Debug；
- **降级可以，无声降级不行。** 拿不到接口要打日志，并让指令如实返回失败。

### 每条负向断言都要配一条正向对照

"没有发生某件坏事"这类断言，在功能整个没跑起来时同样成立。

「拒绝为子窗口创建任务栏按钮」在任务栏接口彻底不可用时照样通过 ——
两种情况都表现为"操作没发生"。所以旁边必须有一条「任务栏接口确实可用」。
同理，「普通窗口没有被 PWA 的组吞掉」旁边必须有「真正同应用的窗口仍会被自动分组」，
否则自动分组开关没开、资格判定拦下、窗口没找到……任何一种都会让它平凡通过。

### 断言基准要选与故障无关的量

同一个功能上还栽过第二跤：拿分组栏底边当基准判断"窗口是否让出了顶部空间"。分组栏一旦被顶出屏幕，底边就是 0，"窗口顶边 ≥ 0" 恒真 —— 这条断言恰好在最该报警的时候保持沉默。

基准必须选与故障无关的量（工作区顶边 + 分组栏高度）。

同理还要有**正向断言**：先确认"整组确实铺满了屏幕"，再谈让位。少了这一条，功能彻底失效（窗口压根没变大）时，让位断言反而全过 —— 一个没铺开的小窗口当然盖不住分组栏。

## 三、测试宿主里的窗口有多听话，测试就有多没用

`tools/TabNest.Harness` 刻意生成一批行为恶劣的窗口。每一种的存在都对应一个真实缺陷。

| 种类 | 模仿对象 | 抓到过什么 |
|---|---|---|
| `stubborn` | Chromium（Electron 外壳的 Claude／VS Code／Slack、Chrome 本身，窗口类 `Chrome_WidgetWin_1`） | 最大化时在 `WM_WINDOWPOSCHANGING` 里把矩形强行改回整个工作区。`SetWindowPos` 返回成功，窗口当场弹回 |
| `hideonclose` | Electron 应用的"关闭即缩托盘" | 关闭窗口时只隐藏、永不发销毁事件。只监听销毁事件的话，窗口没了而标签还在 |
| `fixed` | OpenVPN Connect、各类登录框 | 尺寸被自身约束夹死，上报的回声若被当成"用户改了大小"，会把同组的大窗口一路拽小 |
| `child` | Chrome Legacy Window | 有标题、可见、非工具窗的**子**窗口，从常规特征完全看不出它不该被分组 |
| `pwa` | Chrome 的 PWA 窗口 | 与其他窗口同进程、同窗口类，只有 AppUserModelID 不同。自动分组只比进程名时，组里有一个 PWA 就会把用户新开的浏览器窗口全吞进去 |
| `slow` | 卡住的 IDE | UI 线程阻塞，用来验证同步消息的超时保护 |

「全屏后分组栏仍然可见」曾经用两个普通 WPF 窗口测得全绿，而功能在真实应用上完全失效 —— WPF 窗口老实接受重定位，Chromium 不接受。

**新的疑难窗口应先在 Harness 里复现，再谈修复。**

## 四、几个反直觉的实测结论

这些都是用一次性探针（`dotnet run --file`）在真实窗口上量出来的，不是推断。

**最大化的窗口无法被可靠地就地重定位。** Chromium 系拒绝，UWP 的 `ApplicationFrameWindow` 接受，WPF 接受。因此分组全屏改用"假最大化"：`SW_RESTORE` 变回普通窗口，再手动铺满"工作区减去分组栏"。普通窗口没有那套强制逻辑，实测 Chromium 与 UWP 都稳定落位不弹回。

**DWM 的窗口隐藏（cloak）不能跨进程用。** 对其他进程的窗口调用返回 `0x80070005`。拖动期间需要藏起非权威成员，最终改用停靠到屏外 `x = -32000`。

**图标组资源 ID 是 32512（`IDI_APPLICATION`），不是 1。** 用 1 在所有尺寸上都失败。是枚举了资源之后才确认的。

**基准测试不能在门禁进程内自测。** 早期版本在门禁进程内测自己，空闲 CPU 报 0.16~0.23%；同一份代码作为常驻进程跑是 0.000% —— 差值全是采样循环自己烧的。把自己的开销算进被测对象，会逼着人去优化根本不存在的问题。`--benchmark` 现在测量的是**外部真实常驻进程**。

**源生成器会摧毁属性初始化器。** `System.Text.Json` 源生成的带参构造路径会把每个属性都从 `args[]` 赋值，JSON 里缺失的键写入 CLR 默认值。这与"仅非默认值落盘"的稀疏写入组合起来是致命的：`Enabled: true` 因等于默认值而被省略，读回来变成 `false`，TabNest 每次重启都自我禁用。修复是 `SparseJson.Deserialize` 改为把差分合并到默认值上。当时 147 个测试全绿，因为没有一个覆盖"从磁盘读一份稀疏文件"这条路径。

## 五、拖动性能

拖动分组窗口曾经"卡爆"。根因有三层，前两层是自己造的：

1. **每帧同步写文件日志**，在 UI 线程上。
2. **16 ms 的 `Task.Delay` 合并**，把事件延迟推到 40~80 ms。
3. **真正的结构性原因**：同一进程的多个成员（典型如两个 IDEA 项目窗口）共享同一条 UI 线程。被拖窗口的模态拖动循环每处理一步鼠标移动，都会被我们塞给其他成员的重排消息打断一次 —— 事件到得再快、我们处理得再快都救不了。

解法是**提起—落位**：拖动开始时把非权威成员停靠到屏外，拖动期间零跨进程调用，被拖窗口就是一次纯粹的系统原生拖动；松手时再一次性对齐回来。

停靠而不是隐藏或最小化：任务栏按钮纹丝不动，也没有还原动画。崩溃安全性由快照还原天然覆盖，不需要额外的清理账本。

另外，跨进程 `SetWindowPos` 一律带 `SWP_ASYNCWINDOWPOS`。默认的同步版本会一直等目标线程处理完，目标应用只要在忙（GC、后台索引、重绘），我们的控制队列就被一起卡住，实测能停两秒。

## 六、空闲 CPU 为什么能到零

两点：`SetWinEventHook` 被动投递、全程无轮询；以及位置变化事件**只跟踪组成员**，不理会全系统的窗口移动 —— 后者不做过滤时实测会把空闲 CPU 推到单核 0.5% 以上。
